# ADR-0001 — Arquitetura do v0 do `@agentic-ddd`

- **Status:** Aceito
- **Data:** 2026-10-06
- **Design completo:** [`docs/superpowers/specs/2026-10-06-agentic-ddd-v0-design.md`](../superpowers/specs/2026-10-06-agentic-ddd-v0-design.md)
- **Origem:** [`prompts/#0001-initial.md`](../../prompts/%230001-initial.md)

## Contexto

Queremos um framework open-source sobre NestJS em que entidades, use-cases e operators (agentes de IA que substituem controllers) se autodeclaram por decorators. Um compilador transforma essas declarações em skills (padrão agentskills.io) e em um `AGENTS.md`, servindo tanto ao agente que **opera** o domínio quanto aos agentes que **desenvolvem** o código. O repositório parte de um scaffold NestJS 12 com Bun.

Projetos próximos existem, mas cobrem só pedaços: runtime de agentes governado no Nest (`irzix/nestjs-agentic`), tools MCP a partir de providers Nest (`@rekog/mcp-nest`), geração de guias para agentes de código (Laravel Boost), changes com delta (OpenSpec). Nenhum combina domínio DDD autodeclarado, compilação para skills e operator como porta de entrada.

## Decisões

| # | Decisão | Alternativas descartadas | Por quê |
|---|---|---|---|
| D1 | Repository in-memory no v0; TypeORM na fase de infraestrutura | TypeORM + `sqljs` já no v0; `better-sqlite3` | O critério de aceite não exige banco; foco do v0 é compilador + operator |
| D2 | `bun test` | Vitest (roda em Node) | Um runtime só; Nest DI, snapshots, `z.toJSONSchema` e `BunAdapter.fetch` validados no Bun 1.4.2 |
| D3 | Só `LlmPort` + `FakeLlm` | Adapter Anthropic direto; Vercel AI SDK | Infra fica para depois; o port já carrega payload opaco do provider e só `toolChoice: auto/none` |
| D4 | Pacote único, fronteiras internas, exemplo em `examples/`, escopo `@agentic-ddd` | Bun workspaces desde o início; exemplo dentro de `src/` | Separar em pacotes depois vira mover pastas; `@nestjs-agentic` está ocupado no npm |
| D5 | Arquivos gerados versionados + `compile --check` no CI | Gitignore; híbrido | `--check` e "agente parte do `AGENTS.md`" exigem os arquivos no repositório |
| D6 | Compilador por reflection em runtime (registry → IR → validação → diff → renderers) | AST em build-time; híbrido | Schemas Zod são valores de runtime; `arquivo:linha` sai do stack trace do decorator |
| D7 | IR versionada como `.agentic/domain.lock.json` | IR não versionada | Base do diff semântico sem depender do git |
| D8 | Changes: code-first na criação, proposal-first na manutenção, delta ADDED/MODIFIED/REMOVED, `--check` falha em diff sem change | Changelog automático sem motivo; só proposal-first | Registra o "porquê", que o compilador não infere, e suporta o ciclo documentação → código |
| D9 | Rastreabilidade de testes por ID de regra (`[covers: …]`) | Scaffold de testes; gerar testes de tudo com LLM | Determinístico; regra MODIFIED aponta os testes a revisar |
| D10 | Critérios de aceite estruturados + `agentic-ddd verify` (`done` / `needs-human` / `failed`) | Só gates automáticos; LLM-juiz | Condição de parada objetiva e igual para qualquer agente |
| D11 | `requiresApproval` declarativo → política `allow/deny/require_approval` → `ApprovalPort` síncrono | Políticas dinâmicas; aprovação durável | Mais simples que cobre o v0; a forma interna já admite políticas depois |
| D12 | Eventos emitidos, devolvidos no `tool_result` e no trace; `reactsTo` no v0.1 | `reactsTo` completo ou só sintático no v0 | Aceite exige só emissão; reação traz fila, cascata e reentrância |
| D13 | Pastas por público: bloco gerado no `AGENTS.md`, `.agents/skills/` (+ espelho `.claude/skills/`), `.agentic/`, `changes/` | Tudo em `.agentic/`; skills junto dos módulos | Descoberta automática pelos agentes de código sem misturar skills de runtime com as de dev |
| D14 | Fluxo "declaração primeiro": esqueleto com `notImplemented()`, detectado via `fn.toString()`, como **sinal** para o estado do projeto; nunca aparece em skill | Flag explícita no decorator (`status: 'pending'`); seção "Pendências" na skill de dev | Skills descrevem o domínio e não têm estado; a verdade sobre implementação é o próprio corpo |
| D15 | `uses` obrigatório no `@AgentUseCase`; validação de existência e `emits ⊆ emits dos uses`; `@Invariant` na classe ou no método que a garante; fábricas estáticas no item da entidade | Inferir dependência por camada; inferir pelo corpo; `@Invariant` só na classe | Grafo exato e paralelizável; pega incoerência antes de existir código; invariante só na classe criava ciclo (entidade dependia do teste do método que dependia da entidade) |
| D16 | Estado do projeto como grafo de work items calculado sob demanda (`status`, `next` em ondas, `packet`, `verify --item` com `specHash`); infraestrutura fora do grafo no v0; skill do framework e subagentes gerente/executor no v0.1 | Arquivo de estado versionado; ledger de eventos | Nada a desatualizar, sem conflito de merge entre executores paralelos; permite gerente forte (Opus/Sonnet) e executor barato (Haiku) sem que o executor altere a especificação |

## Consequências

- **Positivas:** fonte única de verdade (código decorado), sem divergência entre descrição e implementação; histórico de regras auditável; agentes de código têm índice, convenções e critério de conclusão objetivo; saída determinística revisável em PR.
- **Negativas / custos:** o subsistema de changes + `verify` tem tamanho comparável ao compilador; proposta e implementação precisam ir no mesmo PR no v0; uma proposta aberta por vez; arquivos gerados aumentam o diff (mitigado por `linguist-generated`).
- **Fora do v0:** `reactsTo`, testes de contrato gerados, runner de eval entre LLMs, canal HTTP, adapter real de LLM, TypeORM, aprovação durável. Ver §13–14 da spec.
