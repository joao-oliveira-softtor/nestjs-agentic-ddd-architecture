# ADR-0008 — Elysia adapter and typed use-case routes

- **Status:** Accepted (decided with the user in a grilling session on 2026-10-28).
- **Date:** 2026-10-28
- **Related:** [ADR-0007](ADR-0007.md) D5, D6 and D11 (operators as MCP tools, server-side context, NestJS as the reference target).

In this ADR, `D1`–`D7` are the decisions of this document.

## Context

The framework only mounted on NestJS (`@agentic-ddd/nestjs`). The operator runtime itself was already framework-free: `AgenticModule` is a DI shell that creates an `OperatorRuntime` and registers operators with injected use-case instances. Users want the same decorated domain on Elysia, and a later goal is for the compiler to produce specifications the frontend consumes. Elysia's Eden already gives end-to-end types from route schemas, and every `@AgentUseCase` already declares its input and output as zod schemas, which Elysia 1.4 accepts as Standard Schema.

## Decisions

| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| D1  | **`@agentic-ddd/elysia` is a second adapter over the same decorated domain.** `agentic({ ...RuntimeOptions, operators, useCases, http? })` returns an Elysia plugin that registers the operators and decorates the app with the runtime as `agentic`. Domain and application code do not change; the import-direction gate bars `elysia` and `@agentic-ddd/elysia` from them, as it bars Nest. Both adapters build the runtime with `createRuntime`, so defaults (deny approval, in-memory bus, registry scoped to the configured modules) are shared.                                                                                                                                                                                                                                                                                                                                                                                                                             | A separate runtime per framework.                                                         |
| D2  | **Use-cases are passed as instances keyed by their `@AgentUseCase` name** (`{ create_order: new CreateOrder(repo) }`). The key gives Eden a literal route name and the instance gives the input/output types; the instance may be of a declared class or of a subclass of one, as Nest's `useClass` allows. Mounting fails when a key differs from the decorator's `name` or the value is not a declared use-case of the configured modules.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | An array of instances: loses the names and types. A hand-written route per use-case.      |
| D3  | **With `http`, each use-case in `http.routes` (default: every one in the map) gets `POST {prefix}/use-cases/<name>`** (default prefix `/agentic`), validated by the decorator's zod `input` and answering its `output`. A `DomainError` answers 422 `{ code, message }`; invalid input answers Elysia's 422 validation body, and both are typed so a client can tell them apart. Only Elysia's own errors reach the app unchanged: `status()`, Elysia's built-in error classes (`NotFoundError`, `ParseError`, `ValidationError`, …) and the exact classes registered with `.error()`. Every other error answers a generic 500 that never carries the error's message: an error from an outside HTTP client, even one with a `status`, a subclass of a registered class, and an output outside its schema. A use-case that an operator lists in `requiresApproval` is mounted only when `http.routes` names it, and mounting fails otherwise. Without `http`, no route is mounted. | One status per error code: needs a new decorator convention. REST-style names per module. |
| D4  | **Direct HTTP calls skip the `ApprovalPort`.** Approval is an operator policy over what the LLM may do alone; a route call is the application acting for its authenticated user. Authentication and authorization belong to the application (mount the plugin inside a guarded group).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | Requiring approval for direct calls.                                                      |
| D5  | **Operators get no HTTP route**, as ADR-0007 D5 decided: they will be MCP tools on the runtime MCP, and their `context` comes only from the server (D6 there). An Elysia app runs an operator with `ctx.agentic.run(name, { message, context })` from its own handler, with context it derives itself.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | `POST /operators/:name/runs` taking `context` from the request body.                      |
| D6  | **Outside an operator, a use-case runs through `executeUseCase`** (`@agentic-ddd/runtime`; routes use `runUseCase`, the same path for an input Elysia already parsed), which applies the same input/output schemas and the same `emits` rule as an operator step. The rule lives in one guard shared by both paths, so it cannot drift. Each call stamps its events with a fresh UUID as correlation and causation id.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | Re-implementing the rule in the adapter. Accepting a client correlation header.           |
| D7  | **`elysia` is an optional peer dependency**; NestJS stays a required peer. Making Nest optional is a separate decision.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |                                                                                           |

## Consequences

- `examples/orders/elysia.ts` mounts the orders domain on Elysia and exports `type OrdersApp` for Eden; `src/elysia/agentic.plugin.test.ts` drives it through `treaty`, and a `@ts-expect-error` on a wrong body proves the types in `typecheck`.
- Eden types a route's body and response from the instance's `UseCase<I, O>` generics, which is the _parsed_ input. For a schema with `transform`, `coerce` or a default, the client-side body type differs from what the schema accepts. The compiler-emitted route table (next steps) closes this by typing from the schema itself.
- One `agentic()` per app, with every module: Elysia keeps the first `agentic` decorator, so a second plugin's runtime would not be reachable through `ctx.agentic`; a second mount fails.
- A use-case publishes its events while it runs, before its output is validated. An output outside its schema therefore answers 500 after the effects and events already happened, just as an operator step fails after publishing. Changing that order is a runtime decision for both paths, out of this change.
- 2026-11-09 (code review of PR #132): D3 used to pass through any error with a numeric `status` in 400–599. An outside client's error (AxiosError, FetchError) has one too, so its status and message (an upstream token problem, a tenant id) reached the client; the rule now passes only the errors Elysia marks as its own, which `.error()` does by stamping the class's prototype with `ERROR_CODE`. That mark is process-wide (registering a class on any Elysia instance marks it for every app) and inherited, so the plugin accepts only the exact registered class: a subclass answers 500, or `.error({ Error })` would let every error through. Registering a base class such as `Error` still lets that exact class through with its message, which is the app's choice; its subclasses still answer 500. The 500 keeps the original on a non-enumerable `cause`, so an `onError` that serializes it does not leak it.
- Next steps, out of this change: declaring HTTP exposure on the decorator and in the IR, so the compiler emits the route table and frontend specifications; routes on the Nest adapter; per-code HTTP statuses for domain errors.
