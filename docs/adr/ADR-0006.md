# ADR-0006 — Modelo de domínio tático: value objects, relações, ports e infraestrutura (v0.5)

- **Status:** Proposto
- **Data:** 2026-10-23
- **Pesquisa:** [`docs/research/2026-10-23-v05-ddd-tatico/relatorio.md`](../research/2026-10-23-v05-ddd-tatico/relatorio.md)
- **Relacionados:**
  - [ADR-0002](ADR-0002.md) (VO como id);
  - [ADR-0003](ADR-0003.md) (packet, brief, gates e o resultado do cycle-21);
  - [ADR-0005](ADR-0005.md) D6 (layout declarado, nunca inferido).

Neste ADR, `D1`–`D10` são as decisões deste documento. Os gates novos se chamam `T1`–`T3` (de "tático"), para não colidir com os gates `G`/`I` nem com as decisões de outros ADRs.

## Contexto

O compilador só conhece entidades, métodos, eventos, use-cases e operators. Value objects, a composição dentro do agregado, a referência entre agregados, os ports (interfaces de repositório) e as implementações de infraestrutura existem no código, mas são invisíveis: não têm spec, packet nem gate, e não entram na ordem das ondas.

Dois exemplos guiam o desenho:
1. **Composição:** `Pedido` contém `ItemDoPedido`, feito de `Quantidade` e `Dinheiro`, e o total é uma invariante do pedido.
2. **Referência entre agregados:** `Matricula` guarda `AlunoId` e `TurmaId`, e "aluno ativo" e "turma com vaga" são regras do use-case `matricular_aluno`.

O piloto cycle-21 também não mediu o ganho do framework: todos os braços o usavam, e três deles bateram no teto de aceite (10 de 10).

A pesquisa comparou quatro propostas (declaração explícita, inferência por tipos, agregado como unidade e medir primeiro), dois julgamentos independentes, spikes e uma revisão adversária. A solução abaixo é a convergência.

## Decisões

| ID | Decisão | Alternativas descartadas |
|---|---|---|
| D1 | **A IR vem só de declaração.** Os decorators registram os dados; a árvore sintática do TS só **confere** (gates T1–T3) e nunca alimenta a IR, o `specHash` nem o packet. O `irHash` continua independente de tsconfig, versão do TS e node_modules. | Inferir as relações pelo TypeChecker (proposta B): o hash passaria a depender do ambiente, e a relação ficaria invisível no diff. |
| D2 | **Byte a byte para quem não usa a feature.** Cada chave nova da IR entra por spread condicional (omitida quando vazia; `undefined` não serve, porque o snapshot do `bun:test` o grava). Seções novas de skill, packet e relatório do `verify` só aparecem quando existe elemento tático. `CORE_RULES` não muda. `irVersion` e `LOCK_VERSION` continuam 1. | Bump de versão da IR/lock: invalidaria todos os locks e skills sem ganho. |
| D3 | **`@AgentValueObject({ description })`** em classe que estende `ValueObject`. É item da camada domain (`valueobject:<Nome>`) e aceita `@Invariant`. Obrigações: o próprio id e as invariantes, cobertas por `covers`. Sinal de esqueleto: a chamada literal `notImplemented()` em qualquer corpo da classe. O VO esqueleto não pode ser instanciado no topo do módulo (ex.: `static ZERO`), senão o `compile` lança erro ao importar. | `@ValueObject`: colide com a classe `ValueObject` de `@agentic-ddd/core`. VO só como classe comum (proposta D): não ganharia contrato nem ordem. |
| D4 | **Relações num sentido só, do dono, sempre com função:** `@AgentEntity({ contains?: () => [VO \| EntidadeFilha], references?: () => [RaizDeOutroAgregado] })`.<br>- `contains` gera `dependsOn` (o contido vem antes do dono).<br>- `references` não gera aresta (ciclos entre agregados continuam permitidos) e leva ao packet o contrato do id e da raiz referenciada.<br>- **Raiz é derivada:** a entidade fora de todo `contains` é raiz.<br>- **Validações:** uma entidade filha só pode estar no `contains` de um dono (VO pode estar em vários); `contains` entre módulos é erro; a função que lança erro ou devolve classe sem decorator gera erro de compilação com o `source` do dono; raiz que não estende `AggregateRoot`, ou filha que estende, é aviso. | Relação declarada nos dois sentidos (proposta A): quebra na ordem de carga das classes. `@Aggregate` separado (proposta C): repete `@AgentEntity`. |
| D5 | **`@Invariant` também em `@AgentUseCase`**, para regras que atravessam agregados (ex.: "aluno ativo"). O id é `invariant:<usecase>/<id>`, que não colide com o de entidade (snake_case vs. PascalCase), com `on: null`. É obrigação do item use-case. `history.ts` e o finder de invariante do MCP passam a resolver o dono por tipo, não supondo entidade. | Deixar a regra só na `description`: ela ficaria sem ID estável e sem obrigação de teste. |
| D6 | **`@AgentPort({ description, root: () => Raiz, methods: { nome: 'descrição' } })`** em **classe abstrata**. É elemento `port:<Nome>`, **sem item próprio**. Os métodos declarados entram na IR, no diff e no `specHash`, e mudar o port exige proposta.<br>- O use-case declara `ports?: () => [Port]`, e o packet dele traz os métodos do port.<br>- O tsc garante a assinatura no adapter.<br>- **Validações:** o `root` precisa ser raiz; todo método abstrato precisa estar em `methods`, e vice-versa. | Interface com decorator: some em runtime. Ler a assinatura da árvore sintática para o packet: contradiz D1. |
| D7 | **`@AgentAdapter({ description, implements: () => Port })`** é **item de uma camada nova, `infrastructure`** (`adapter:<Nome>`), com `dependsOn` = a raiz do port.<br>- Obrigações: um id `port:<Port>.<método>` por método declarado, coberto por `covers` literal no teste do adapter. É o que garante, por exemplo, o `contarPorTurma` usado em "turma com vaga".<br>- Validação: `Adapter.prototype instanceof Port`.<br>- Novos: papel e brief do executor de infraestrutura (o `roleForLayer` aceita a camada) e `--layer infrastructure` no `boundary-gates`. A infra pode importar libs externas; domain e application continuam proibidos de importar infra.<br>- O módulo do adapter não pode ter efeito colateral no import (o `compile` importa todo `.ts` do módulo); conexões ficam no construtor ou na fábrica. | `repositoryContract` genérico em `@agentic-ddd/testing`: geraria testes dinâmicos, que o `status --static` não vê; exigiria `bun:test` na lib; cobriria só `findById`/`save`. Port como item: não há corpo para implementar. |
| D8 | **Escopo de classe para itens de VO e adapter.** O executor altera os corpos e os campos `#privados` da classe inteira, mas não os decorators, o `extends`/`implements` nem a assinatura pública. Um gate de escopo de classe (`boundary-gates`) confere isso, e o brief desses itens diz isso, não "interior de `Classe.método`". | Manter só o gate de corpo de método: o executor não conseguiria implementar um VO nem um adapter sem violá-lo. |
| D9 | **Gates táticos determinísticos (árvore sintática + metadados).** Entram no `verify` do item dono como um gate `T` que só aparece no relatório quando o projeto tem elemento tático (D2).<br>- **T1, referência só por id:** um campo ou uma *parameter property* do construtor (inclusive `#privado`, `readonly`, `Array`/`Set`/`Map`) cuja anotação de tipo nomeia a raiz de **outro** agregado é violação. Parâmetro comum de método não conta. Fonte: JMoleculesDddRules `aggregateReferencesShouldBeViaIdOrAssociation`.<br>- **T2, VO não referencia entidade:** a mesma checagem sobre os campos do VO. Fonte: `valueObjectsMustNotReferToIdentifiables`.<br>- **T3, declarado = usado:** um campo do dono que nomeia um VO ou uma entidade filha fora do `contains` é violação.<br>- **Falso negativo conhecido** (vai para a doc): alias de tipo e tipo inferido sem anotação. | Gates pelo TypeChecker: ficam para a v0.6, depois de uma spike de custo e determinismo com barrels e monorepo. "Um agregado mutado por use-case": exige separar leitura e escrita em `uses`. |
| D10 | **Medir o ganho do framework** com um braço de controle, pré-registrado antes de rodar.<br>- **Braços:** C0, packet mínimo (id do item, arquivo e comando de teste), sem skill, sem regras do brief e sem gates no laço; e F, o framework completo.<br>- **Condições:** mesma versão (v0.5), mesmo esqueleto declarado, mesmo modelo (`inherit`), comparação pareada por item.<br>- **Tarefas:** um tutorial novo, "matrículas", com armadilhas plantadas: tentação de guardar `Aluno` inteiro, regra que atravessa agregados, VO com invariante e repositório com consulta própria.<br>- **Métricas:** aceite pelo oráculo privado; violações T1/T2 (os decorators estão no esqueleto dos dois braços); defeitos dos testes privados de cada armadilha. "Inconclusivo" é um resultado previsto.<br>- **Harness:** `benchmark` aceita `matriculas`, modo de prompt `bare` e `TASK_ITEMS` por tutorial. | Rodar o C0 na v0.4 e o F na v0.5: mistura versão com tratamento. Só aceite como métrica: bateu no teto no cycle-21. |

## Decisão de domínio do tutorial (não do framework)

"Turma com vaga" é conferida pelo use-case, contando as matrículas da turma pelo `MatriculaRepository.contarPorTurma`. A `Turma` não é mutada, e um único agregado (a `Matricula`) é criado por transação, como Vernon recomenda.

Isso **não** é uma invariante transacional: duas matrículas simultâneas podem passar ao mesmo tempo. O tutorial documenta essa corrida, e a solução real (bloqueio ou reserva na `Turma`) fica a cargo de cada domínio.

## Exemplos no modelo

```ts
@AgentValueObject({ description: 'Valor monetário em centavos.' })
@Invariant({ id: 'nao-negativo', text: 'Dinheiro não é negativo.' })
export class Dinheiro extends ValueObject<{ centavos: number; moeda: string }> { /* ... */ }

@AgentEntity({ description: '...', states: [...], contains: () => [ItemDoPedido, Dinheiro] })
@Invariant({ id: 'total-soma-itens', text: 'O total é a soma dos itens.' })
export class Pedido extends AggregateRoot<string> { /* ... */ }

@AgentEntity({ description: '...', states: [...], contains: () => [AlunoId, TurmaId], references: () => [Aluno, Turma] })
export class Matricula extends AggregateRoot<string> { /* ... */ }

@AgentPort({ description: '...', root: () => Matricula, methods: { save: 'Grava a matrícula.', contarPorTurma: 'Conta as matrículas ativas da turma.' } })
export abstract class MatriculaRepository { /* métodos abstratos */ }

@AgentUseCase({ name: 'matricular_aluno', /* ... */ ports: () => [MatriculaRepository, AlunoRepository, TurmaRepository] })
@Invariant({ id: 'aluno-ativo', text: 'Só aluno ativo se matricula.' })
@Invariant({ id: 'turma-com-vaga', text: 'A turma precisa ter vaga.' })
export class MatricularAluno { /* ... */ }

@AgentAdapter({ description: 'Repositório em memória.', implements: () => MatriculaRepository })
export class InMemoryMatriculaRepository extends MatriculaRepository { /* ... */ }
```

Ordem das ondas:
- `AlunoId`, `TurmaId`, `Dinheiro` e `Quantidade`;
- depois `ItemDoPedido`;
- depois `Pedido`, `Aluno`, `Turma` e `Matricula`;
- depois os métodos;
- depois os use-cases e os adapters.

O `Pedido` fica numa fixture do compilador. O `matrículas` é o tutorial novo; `examples/orders` não muda.

## Consequências

- **Positivas:**
  - VO e infraestrutura ganham contrato, ordem e verificação, e as regras táticas mais citadas (jMolecules, Vernon) viram gate;
  - quem não usa a feature não vê nenhuma diferença;
  - o ganho do framework passa a ser medido com controle.
- **Negativas / custos:**
  - 3 decorators novos e 1 camada nova;
  - gates com falso negativo conhecido;
  - um tutorial novo para manter;
  - o harness ganha um modo de prompt e um benchmark;
  - a execução do experimento exige orçamento de inferência autorizado à parte.
- **Migração e rollback:** nada migra, porque tudo é opt-in. Reverter é reverter os PRs, e os snapshots atuais continuam válidos.
- **Fica para a v0.6+:**
  - gates pelo TypeChecker;
  - um agregado mutado por use-case;
  - regras de corpo (efeito por evento, invariante só com campos do agregado);
  - VO imutável;
  - finders novos no MCP;
  - adapters que não sejam repositório;
  - rascunho de adoção para projeto existente.
