# ADR-0002 — Igualdade de `Entity` quando o id é um value object

- **Status:** Aceito (opção B, 2026-10-13)
- **Data:** 2026-10-12 (proposto); aceito em 2026-10-13
- **Origem:** achado F6 do code review, tratado na Fase 5 de [`docs/superpowers/plans/2026-10-12-code-review-fixes.md`](../superpowers/plans/2026-10-12-code-review-fixes.md)

## Contexto

Até a proposta, `Entity<Id>.equals` (`src/core/entity.ts`) comparava classe e id com `===`:

```ts
other != null && other.constructor === this.constructor && other.id === this.id;
```

Com id primitivo (o caso de `Order`, que usa `string`), isso é correto. Com id que é um `ValueObject` (por exemplo `Entity<OrderId>`), `===` compara referências: duas entidades da mesma classe cujos ids são `OrderId` diferentes em memória, mas iguais por valor, nunca são `equals`. O `ValueObject.equals` do mesmo pacote existe justamente para essa comparação por valor, e `Entity` não o usa.

Hoje nenhum código do repositório usa id que não seja `string` (`examples/orders`, fixture `shop`), então a decisão não altera nada existente. Ela define o contrato do `core` para quem modelar ids como value objects, algo comum em DDD.

## Opções

| #   | Opção                                                           | Prós                                                                                     | Contras                                                                                                                                     |
| --- | --------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| A   | Manter `===`                                                    | Nenhuma mudança; semântica simples                                                       | Id-VO nunca iguala por valor; a armadilha só aparece em uso                                                                                 |
| B   | Delegar a `ValueObject.equals` quando o id for um `ValueObject` | Corrige o caso sem mudar o de id primitivo; a comparação por valor já existe e é testada | `Entity` passa a conhecer `ValueObject` (mesmo pacote, sem dependência nova); id-VO de classes diferentes continua diferente por construção |
| C   | Exigir id primitivo (restringir `Id`)                           | Contrato explícito; `===` passa a ser sempre correto                                     | Quebra a API pública (`Entity<Id>` hoje aceita qualquer tipo) e proíbe ids tipados, o que é comum em DDD                                    |

## Decisão

Opção **B**:

```ts
equals(other: Entity<Id> | null | undefined): boolean {
  if (other == null || other.constructor !== this.constructor) return false;
  return this.id instanceof ValueObject && other.id instanceof ValueObject
    ? this.id.equals(other.id)
    : other.id === this.id;
}
```

O `instanceof` em `other.id` também é necessário: sem ele o `tsc` rejeita `this.id.equals(other.id)` (`Id` não é atribuível a `ValueObject`). A forma acima foi conferida com `bun run typecheck`.

Motivos: é a única opção que corrige o caso sem quebrar a API e sem alterar o comportamento de ids primitivos. `src/core` continua importando só `zod`.

**Aceite:** o usuário aceitou a opção B em 2026-10-13. O teste de caracterização de `src/core/core.test.ts` foi invertido para exigir a igualdade por valor (escrito antes da mudança e visto falhando) e a implementação acima entrou em `Entity.equals`, com o JSDoc atualizado.

## Consequências

- **Aceita (B):** entidades com id-VO passam a se igualar por valor do id; id primitivo não muda; entrou um desvio em `Entity.equals` (uma ramificação) e um teste novo.
- **Limites da B:** a delegação cobre só `ValueObject`. Ids compostos que são objetos simples (`{ a, b }`) ou `Date` continuam comparados por `===`. Se o `core` for carregado em duas cópias (por exemplo `@agentic-ddd/core` e o código-fonte em `src` no mesmo processo), o `instanceof` falha em silêncio e o código volta ao `===` sem erro.
- **Se rejeitada (A):** permanece a limitação documentada; quem usa id-VO compara `a.id.equals(b.id)` por conta própria.
- **Se C for preferida:** exige mudança de tipo em `Entity`/`AggregateRoot` e é uma quebra de API, a tratar num PR próprio.
- **Em qualquer caso:** o JSDoc de `Entity.equals` deve dizer qual é o contrato vigente.
