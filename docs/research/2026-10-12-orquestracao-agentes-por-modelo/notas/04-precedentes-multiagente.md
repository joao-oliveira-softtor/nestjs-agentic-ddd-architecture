# Multi-agent / role-specialized SWE agent systems and spec-driven workflows: precedents for a layered "cheap worker / mid-tier integrator / strong reviewer" pipeline

Research date: 2026-10-12. Labels: [MEASURED] = number from a paper/benchmark/vendor table; [VENDOR] = vendor self-report, not independently verified; [ANECDOTAL] = design opinion or blog narrative; [PROPOSAL] = design or position with no results. Several 2026 arXiv items were read only at abstract level (flagged).

## 1. Per-system survey: roles, model assignment, handoff artifact, context isolation, measured results

### Takeaway
No surveyed system implements the exact "cheap worker on narrow units, mid-tier integrator across layers, strong reviewer" split with all three tiers. The closest precedents are: Aider architect/editor (two tiers, strong planner plus cheap editor, measured), Anthropic's research system (strong lead, cheaper subagents, measured on research only), Cursor's planner/worker/judge (role-specific model choice, anecdotal results at scale), Cognition's "clean-context reviewer" and "Smart Friend" (reviewer and escalation patterns), and MetaGPT/CodeTeam/ProjectGen (architect-authored contracts consumed by implementers). The handoff artifact is almost always a structured document (PRD/design/interfaces, spec/plan/tasks, or a machine-checkable contract), not chat.

### Cited Findings

**Role-play "software company" systems (2023-24)**
- MetaGPT: five roles (Product Manager, Architect, Project Manager, Engineer, QA). Agents hand off structured documents (PRD, system design, interface definitions, file list) rather than free chat. A publish-subscribe message pool gives each role only relevant information. The Engineer runs code and unit tests with up to 3 retries. [MEASURED] 85.9% Pass@1 HumanEval, 87.7% MBPP; executable feedback adds ~4.2% / ~5.4%; on SoftwareDev vs ChatDev executability 3.75 vs 2.25, human revision cost 0.83 vs 2.5, ~124 vs ~249 tokens per line of code. Role ablation: adding roles beyond Engineer generally raises executability and cuts revisions at modest cost. Limitations: no UI/front-end, struggles with complex real-world requirements. — [MetaGPT arXiv HTML](https://arxiv.org/html/2308.00352v7); abstract: [arXiv](https://arxiv.org/abs/2308.00352)
- ChatDev: roles CEO/CTO/programmer/reviewer/tester; chat chain of design -> coding -> testing (~5 subtasks); only solutions, not full dialogue histories, carry between phases (a form of context isolation); "communicative dehallucination" (assistant asks instructor for specifics before answering). [MEASURED, on its own benchmark] outperforms GPT-Engineer and MetaGPT on completeness, executability, consistency, quality; removing role assignment had the largest ablation effect. Costs more tokens/time than single-agent GPT-Engineer. Authors say it suits prototypes more than complex real-world systems; agents produce low-information-density logic. — [ChatDev arXiv v5](https://arxiv.org/html/2307.07924v5). Note: a secondary summary reports quality 0.3953 vs MetaGPT 0.1523; unverified against the paper tables — [search summary](https://arxiv.org/pdf/2307.07924). A later third-party analysis (MAST) found MetaGPT had 60-68% fewer system-design and misalignment failures than ChatDev but 1.56x more verification failures — [MAST paper](https://arxiv.org/html/2503.13657v3). Competing claims across papers: each paper's own benchmark favors itself.
- AgentCoder: three agents (programmer, test designer, test executor); the tester is a separate agent from the author of the code. [MEASURED, function-level only] GPT-4: 96.3% pass@1 HumanEval, 91.8% MBPP, token overhead 56.9K / 66.3K vs prior SOTA 90.2% / 78.9% at 138.2K / 206.5K. The page did not state the claim that independent test generation avoids bias; that is the usual rationale but not confirmed in what I read. — [AgentCoder arXiv](https://arxiv.org/abs/2312.13010)

**Single-agent / pipeline / tool-interface systems**
- SWE-agent: contribution is the agent-computer interface (ACI), not role splitting; single agent. [MEASURED] 12.5% pass@1 SWE-bench (full, at publication), 87.7% HumanEvalFix. — [SWE-agent arXiv](https://arxiv.org/abs/2405.15793)
- OpenHands: open platform; default CodeAct agent; a delegation primitive (AgentDelegateAction) reported only by a secondary blog, not confirmed. [MEASURED via secondary] CodeActAgent (Claude-3.5-Sonnet) 26.0% SWE-bench Lite, comparable to Aider 26.3%. — [secondary summary](https://themoonlight.io/fr/review/openhands-an-open-platform-for-ai-software-developers-as-generalist-agents); paper arXiv 2407.16741 not opened.
- Agentless (UIUC): fixed three-phase pipeline (hierarchical localization file -> class/function -> edit location; repair by sampling multiple Search/Replace patches; validation with generated reproduction tests, regression tests and majority vote). LLM does not choose actions. [MEASURED] 96/300 = 32.00% SWE-bench Lite at ~$0.70 per issue (FSE version 32.67%, $0.68); 194/500 = 38.80% on Verified. Authors' critique of agents: complex tool use, no control of planning (30-40 turns), weak self-reflection. Only 213 generated reproduction tests actually reproduced the issue; of those only 94 pass on the gold patch, i.e. LLM-generated verifiers are noisy. Also found problematic SWE-bench Lite items (leaked/misleading patches) and made Lite-S (249 items). — [Agentless arXiv v2](https://arxiv.org/html/2407.01489v2); [FSE listing](https://conf.researchr.org/details/fse-2025/fse-2025-research-papers/85/Demystifying-LLM-based-Software-Engineering-Agents)

**Aider architect/editor (closest measured analogue to planner + cheap implementer)**
- Architect describes how to solve the problem; Editor turns that into concrete file edits. Motivation: o1 reasons well but often fails to emit properly formatted edit instructions. — [Aider architect post](https://aider.chat/2024/09/26/architect.html)
- [MEASURED, aider code-editing benchmark] o1-preview+o1-mini 85.0%; o1-preview+DeepSeek (whole) 85.0%; o1-preview+Sonnet (diff) 82.7%; o1-preview alone 79.7%; Sonnet+Sonnet 80.5% vs Sonnet alone 77.4%; GPT-4o+GPT-4o 75.2% vs 71.4% alone; GPT-4o architect + DeepSeek editor 74.4%. — same source. Gains from pairing are modest (3 to 6 points) and in the same-model case come only from separating "think" from "format edit".
- [MEASURED, polyglot benchmark] R1 architect + Sonnet editor 64.0% at $13.29 vs o1 61.7% at $186.5 (~14x cheaper); R1 alone 56.9% ($5.42); Sonnet alone 51.6% ($14.41); 100% correct edit format for the pair. — [Aider R1+Sonnet post](https://aider.chat/2025/01/24/r1-sonnet.html)
- Cognition notes edit-apply split is fragile: "the small model would misinterpret the instructions of the large model" — [Cognition](https://cognition.com/blog/dont-build-multi-agents)

**Cognition / Devin**
- "Don't Build Multi-Agents" (June 2025) [ANECDOTAL/position]: two principles, "share context, and share full agent traces" and "actions carry implicit decisions, and conflicting decisions carry bad results". Flappy Bird example: one subagent built a Mario-style background, another a non-Flappy bird; merging failed. Recommends a single-threaded linear agent, with a context-compression model for long tasks. Says Claude Code subagents never work in parallel with the main agent and are usually only asked to answer questions, not write code. — [Cognition](https://cognition.com/blog/dont-build-multi-agents)
- "Multi-Agents: What's Actually Working" (April 2026 per search summary) [VENDOR]: thesis "writes stay single-threaded and the additional agents contribute intelligence rather than actions". Patterns: (a) clean-context reviewer loop (Devin Review sees only the diff; best results when reviewer shares no prior context); (b) a "communication bridge" where the coder filters reviewer findings using user instructions to prevent loops and scope creep; (c) "Smart Friend": small fast primary (SWE-1.5, ~950 tok/s) escalates to a larger model (Sonnet 4.5) as a tool with a fork of its context; ceiling was the primary's judgment about when to escalate; (d) manager Devin spawning child Devins ("map-reduce-and-manage"); (e) Claude+GPT routed per subtask. [MEASURED, vendor] Devin Review finds ~2 bugs per Devin-written PR on average, ~58% severe. Failure modes listed: conflicting implicit decisions from parallel writers, endless review loops, weak primary not escalating, Smart Friend hallucinating when primary never read relevant files, over-prescriptive managers, children assuming shared state, children not reporting upward, context rot. — [Cognition](https://cognition.com/blog/multi-agents-working)

**Anthropic**
- Multi-agent research system [MEASURED, internal research eval]: Opus 4 lead + Sonnet 4 subagents beat single Opus 4 by 90.2%; multi-agent uses ~15x tokens of chat (agents ~4x); token usage alone explained ~80% of variance on BrowseComp. Subagent briefs need "an objective, an output format, guidance on tools and sources, and clear task boundaries"; vague briefs caused duplicate work and gaps. Subagents can write outputs to external storage and return lightweight references to cut information loss, "especially for structured outputs like code". Explicitly: "most coding tasks involve fewer truly parallelizable tasks than research." — [Anthropic engineering](https://www.anthropic.com/engineering/multi-agent-research-system)
- Building Effective Agents: orchestrator-workers (central LLM decomposes dynamically; cited use case is multi-file coding changes) and evaluator-optimizer (needs clear evaluation criteria). Coding is verifiable via tests; "human review remains crucial for ensuring solutions align with broader system requirements"; use the simplest solution, add complexity only when it demonstrably improves outcomes. — [Anthropic](https://www.anthropic.com/engineering/building-effective-agents)
- Claude Code subagents (docs): each subagent runs in its own context window with its own system prompt, tool allowlist and permissions; non-fork subagents see only the delegation prompt plus CLAUDE.md and a git snapshot; only a final summary returns to the parent. Per-subagent `model` field (sonnet/opus/haiku/inherit), e.g. route exploration to a cheap model. Optional `isolation: worktree`. Guidance: use main conversation when phases share significant context or need iteration; subagents for self-contained work returning a summary. Nesting allowed up to a depth limit; up to 20 concurrent. — [Claude Code docs](https://code.claude.com/docs/en/sub-agents)

**Cursor**
- "Scaling agents" [VENDOR/ANECDOTAL]: flat agents coordinating through a shared file with locks failed (20 agents performed like 2-3); optimistic concurrency was better but flat agents became risk-averse. Working design: planners (can spawn sub-planners) create tasks; workers focus only on their task and push without coordinating; a judge decides at cycle end whether to continue; fresh start per iteration. Model per role (GPT-5.2 better planner/long-runner than GPT-5.1-Codex; Opus 4.5 tended to stop early). An integrator/conflict-resolver role "created bottlenecks" and was removed. Outputs: browser from scratch (~1 week, >1M LOC), Solid-to-React migration (+266K/-193K) "passing CI and early checks but still needed careful review". Lesson: "prompts matter more" than harness/models; remove components rather than add. — [Cursor blog](https://cursor.com/blog/scaling-agents)
- Windsurf agent modes: not researched (gap).

**Cline/Roo**
- Roo Orchestrator/Boomerang: orchestrator splits a task into subtasks, each in a specialized mode (Code, Architect, Debug); subtasks run in "complete isolation with its own conversation history"; information flows down only via the creation instructions and up only via an `attempt_completion` summary. Orchestrator has no file/command tools by default. Approval gates on subtask creation and completion by default. Handoffs are lossy by design. The page does not cover per-mode model assignment. — [Roo docs](https://roocodeinc.github.io/Roo-Code/features/boomerang-tasks). Cline plan/act mode: not fetched (gap).

**Spec-driven tools**
- Kiro (AWS): three markdown files per spec in `.kiro/specs/`: requirements.md (user stories + EARS acceptance criteria "WHEN ... THE SYSTEM SHALL ..."), design.md (architecture, sequence diagrams, implementation considerations), tasks.md (discrete trackable tasks, status updated as work proceeds). Requirements-First (requirements -> design -> tasks) or Design-First; Quick Spec generates all three in one pass without approval gates; docs recommend editing requirements/design then "Sync Files" on tasks.md. Multiple secondary sources add that design.md holds TypeScript interfaces/data flow/API endpoints and tasks link back to requirements. — [Kiro docs](https://kiro.dev/docs/specs/), [Kiro feature specs](https://kiro.dev/docs/specs/feature-specs/), [Kiro best practices](https://kiro.dev/docs/specs/best-practices/) (as summarized by search; I did not fetch the pages directly), [SD Times](https://sdtimes.com/?p=57508). No measured results found.
- GitHub spec-kit: commands constitution (project principles), specify, plan, tasks, implement, converge (repeat implement/converge until "Converged"); clarification, checklists and consistency analysis as extra quality gates; bug-fix flow warns "Missing verification is not a successful fix". No quantitative claims. — [spec-kit repo](https://github.com/github/spec-kit)
- OpenSpec: `openspec/specs/` (current truth) and `openspec/changes/<change>/` containing proposal.md, specs/ (ADDED/etc. requirement deltas with WHEN/THEN scenarios), design.md, tasks.md; lifecycle explore -> propose -> apply -> archive (archive merges deltas into specs); "built for brownfield"; self-described as lighter than spec-kit (rigid phase gates) and not tied to an IDE as Kiro is. Human reviews the plan before code. [project self-description, no measurements] — [OpenSpec repo](https://github.com/Fission-AI/OpenSpec)
- Empirical SDD research is nascent (2026): Tufano et al., spec-first test generation agent on Google production bugs: [MEASURED] +9.8 pp bug detection (p=0.035), +2.5 pp branch coverage, LLM-judge preferred suite in 77.8% of cases vs baseline — [arXiv 2608.17177](https://arxiv.org/abs/2608.17177). CodeSpec (dual executable specifications: architecture + behavior) on FeatureBench with DeepSeek-V4-Pro: 70.7/55.0/49.9% pass rates, reported above Claude Code baseline, abstract-level only — [arXiv 2607.26777](https://arxiv.org/abs/2607.26777). SpecMine corpus of SDD artifacts across 18 tools and SDAD technical report exist (search listing only) — [search result list](https://arxiv.org/pdf/2608.25202), [SDAD](https://arxiv.org/pdf/2608.20341).

### Inferences
- The proposed pipeline's strongest empirical support is for (1) planner/implementer splits (Aider), (2) structured-document handoffs (MetaGPT, Kiro, OpenSpec, CodeTeam contracts), and (3) fresh-context reviewer (Cognition, Devin Review). The middle "integrator" tier has the least direct precedent; Cursor removed its integrator role as a bottleneck, while Cognition's critique targets parallel writers and not sequential layered ones.
- Context isolation is the shared default (Claude Code, Roo, ChatDev phase carry-over); the loss is always handoff fidelity, so artifact quality determines outcome.
- The user's repo already matches the OpenSpec-style loop (proposal in `changes/NNNN-slug`, packet, verify with spec-hash), so OpenSpec/Kiro are the most direct analogues for the workflow and Aider/Anthropic for model tiering.

### Gaps
- Primary-source numbers for Cline plan/act, Windsurf modes, Devin architecture details, OpenHands delegation, and Claude Code plan mode as a measured pattern were not obtained.
- Kiro, spec-kit and OpenSpec have no controlled evaluations I could find; Kiro docs were summarized by search results rather than fetched.
- No measured results for the exact three-tier cost/quality split.

## 2. Layer-by-layer / bounded-context decomposition, and LLM-generated DDD / hexagonal code

### Takeaway
I found no study that evaluates different agents owning domain vs application vs infrastructure layers. Evidence is adjacent: (a) architecture-first, contract-first repo generators (CodeTeam, ProjectGen) that decompose by file/module ownership rather than DDD layer; (b) a pilot showing weaker models violate hexagonal boundaries; (c) a DDD prompting study showing errors compound in later steps. Role-based teams still lag human code on repo-scale tasks.

### Cited Findings
- Architectural violations under pressure [MEASURED, small pilot, N=5 per model, temperature 0.2]: asked for a hexagonal Book Lending microservice (domain free of external dependencies) with a conflicting request for in-memory caching in domain `get_book`. Architectural violation rate: GPT-5.1 0%, Claude 4.5 Sonnet 20% (1 of 5, minor), Llama 3 8B 80% (4 of 5, domain importing infrastructure, "Hallucinated Coupling"). Llama stubbed work ("Implementation Laziness") with ~91 LLOC vs 225-240. Maintainability Index was higher for the lazy output (66 vs 42-45), so a MI-based gate is misleading. Author recommends automated import linters / ArchUnit-style checks. Caveats: model size confounded with openness, small N, text/table inconsistency. — [arXiv 2512.04273](https://arxiv.org/html/2512.04273v1)
- DDD with LLMs [MEASURED qualitatively, one industrial case]: a five-step prompting framework (ubiquitous language, event-storming simulation, bounded contexts, aggregates, mapping to technical architecture). Steps 1-3 gave usable artifacts; errors compounded so that aggregate design and architecture mapping (steps 4-5) were "impractical"; best as a sparring partner, human decisions remain central. — [arXiv 2603.26244](https://arxiv.org/abs/2603.26244)
- CodeTeam (June 2026; abstract only): multiple Architect agents draft competing design sketches; a CTO agent selects one and produces a machine-checkable contract covering file ownership, public interfaces and dependency constraints; Developer agents implement under a dependency-aware scheduler with bounded context; QA agent runs tests and repairs. [MEASURED] NL2Repo-Bench average test pass 34.6% (prompt-engineering) / 42.3% (SFT), highest vs baselines; ablations: project-specific developer allocation +9.9% and retrieval-augmented planning +8.1% relative SketchBLEU. Models not named in abstract. — [arXiv 2606.22082](https://arxiv.org/abs/2606.22082)
- ProjectGen (Nov 2025): stages architecture design -> skeleton generation -> code filling, built around a Semantic Software Architecture Tree; DevBench 52/124 tests (+57% vs baselines), CodeProjectEval 310 tests (~10x baselines). Baselines unnamed in abstract. — [arXiv 2511.03404](https://arxiv.org/abs/2511.03404)
- NL2Repo-Bench is reported (via a search summary of CodeTeam's related work) to show that agents lose global architectural consistency and write brittle cross-file dependencies — [search summary](https://arxiv.org/pdf/2606.22082); primary not opened.
- Role-based multi-agent generation on 12 Java repositories produced code closer to developer-written code than single LLMs but still short of human implementations; earlier frameworks like MetaGPT had mostly been tested on function-level or <10-file projects (abstract-level) — [arXiv 2607.04212](https://arxiv.org/abs/2607.04212)
- Added layers do not automatically help: on all 164 HumanEval tasks with GPT-4o-family models (1,968 paired observations), analyst/coder split and tester layers raised code complexity by 50-130% with no pass@1 gain; leaner architectures matched or beat heavier ones — [arXiv 2606.00308](https://arxiv.org/abs/2606.00308) (function-level only, not layered-architecture code).
- Kiro's design.md carries interfaces, data flow and API definitions as the cross-layer contract, per secondary reports — [SD Times](https://sdtimes.com/?p=57508) / [InfoWorld](https://www.infoworld.com/article/4023980/from-prompts-to-specs-awss-kiro-signals-the-next-phase-of-ai-coding-tools.html).

### Inferences
- Decomposing by DDD layer is novel relative to the literature; the literature decomposes by role (analyst/architect/dev/QA) or by file/module with contract ownership. A layer-based split maps naturally onto "file ownership + public interfaces + dependency constraints", i.e. CodeTeam's contract, with the dependency direction (domain <- application <- infrastructure) being a deterministic lint rule.
- Boundary violations are cheap to detect mechanically (import-direction lint), which is where the cheap-worker risk (Hallucinated Coupling, stubbing) is concentrated.
- DDD step-4/5 findings suggest strategic design (aggregates, boundaries) should be human or strong-model authored, not delegated downward.

### Gaps
- No study of duplicated abstractions or naming drift specifically between layered agents; those pitfalls are inferred from general MAS misalignment and Cognition's implicit-decisions argument.
- No evidence on clean-architecture/DDD code quality from LLM agents beyond the single pilot above.

## 3. Multi-agent failure modes and when single agent beats multi-agent

### Takeaway
MAS failures are mostly design, misalignment and verification problems, not just base-model limits. Coding parallelism is weak: coupled writes produce conflicting implicit decisions. Concrete mitigations converge on explicit role/task specs, a verification step against the real objective, single-threaded writes, and deterministic gates.

### Cited Findings
- MAST (Cemri et al., NeurIPS 2025 D&B): 14 failure modes in 3 categories from 1,642 traces across 7 open-source MAS; failure rates 41% to 86.7%; annotator kappa 0.88; LLM annotator 94% accuracy. [MEASURED] Category sums (computed from per-mode figures): FC1 system design ~44.2% (disobey task spec 11.8, disobey role spec 1.5, step repetition 15.7, loss of conversation history 2.8, unaware of termination 12.4); FC2 inter-agent misalignment ~32.4% (conversation reset 2.2, fail to ask clarification 6.8, task derailment 7.4, information withholding 0.85, ignored other agent's input 1.9, reasoning-action mismatch 13.2); FC3 task verification ~23.5% (premature termination 6.2, no/incomplete verification 8.2, incorrect verification 9.1). Verifiers often do superficial checks (e.g. "it compiles"). — [MAST arXiv v3](https://arxiv.org/html/2503.13657v3); venue [NeurIPS poster](https://neurips.cc/virtual/2025/poster/121528)
- MAST interventions [MEASURED]: ChatDev improved role specifications +9.4% task success (same prompt, GPT-4o); adding a high-level task-objective verification step +15.6% on ProgramDev. Authors say tactical fixes are inconsistent and do not resolve all modes. Architecture effects: MetaGPT (assembly line) vs ChatDev (hierarchical): fewer FC1/FC2 but more FC3 failures; HyperAgent on SWE-Bench Lite dominated by step repetition and incorrect verification. GPT-4o had 39% fewer FC1 failures than Claude 3.7 Sonnet in MetaGPT. — same source
- Single vs multi: UIUC (Gao et al., May 2025) reports the accuracy gap between single and multi-agent systems narrows as frontier LLMs improve while cost gap widens; a cascading hybrid improved accuracy 1.1-12% and cut cost up to 20% [MEASURED, various agentic apps, not coding-specific] — [arXiv 2505.18286](https://arxiv.org/pdf/2505.18286). A search-result summary of an agent-framework evaluation (arXiv 2511.00872) says multi-agent systems had more steps, better completeness but worse executability on software development — [search listing](https://arxiv.org/pdf/2511.00872), primary unverified.
- MSEval (2026, abstract-level) [MEASURED]: across 10 full-stack projects and 10 topologies (100 runs), changing only team structure shifted scores by >30 points and doubled wall-clock; structured pipelines converged fastest with highest quality; heavy managerial oversight degraded performance — [arXiv 2607.27877](https://arxiv.org/abs/2607.27877)
- Anthropic: multi-agent ~15x tokens, suits parallelizable, large-context, many-tool work; coding has fewer parallelizable parts — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system). Cognition: parallel writers conflict; single-threaded linear agent plus context compression — [Cognition](https://cognition.com/blog/dont-build-multi-agents). LangChain's Harrison Chase reconciles the two as task-type differences (reported by search summary) — [LangChain](https://blog.langchain.com/how-and-when-to-build-multi-agent-systems).
- Cursor: removing the integrator role and keeping workers independent outperformed more structure; flat shared-state coordination failed — [Cursor](https://cursor.com/blog/scaling-agents). Contrast: Cognition's later view that manager/child delegation works only with deep codebase context for the manager — [Cognition](https://cognition.com/blog/multi-agents-working).
- Simplicity advice: use the simplest solution, justify complexity by measured outcomes — [Anthropic](https://www.anthropic.com/engineering/building-effective-agents).

### Inferences
- Mitigations mapped to MAST: FC1 -> explicit, narrow task specs and role boundaries (reduces disobey-spec and derailment); FC2 -> structured handoff packets and a way for workers to ask/raise blockers upward (Cognition lists missing upward communication); FC3 -> verifier checks the objective, not just compilation, and a separate reviewer with clean context.
- A layered pipeline is sequential rather than parallel-writer, so Cognition's strongest objection applies less, but implicit decisions (naming, error conventions, DTO shapes) still need to live in the contract.
- Heavy manager layers can hurt (MSEval, Cursor); keep the integrator as an executor of explicit gates rather than a free-form coordinator.

### Gaps
- MAST per-framework rates exist only in figures I did not see; only the 41-86.7% range is quoted. MSEval, UIUC and 2511.00872 were read at abstract/summary level.
- No controlled comparison of "cheap model on narrow spec" vs "strong model single-agent" on coded-to-contract tasks.

## 4. Handoff artifacts and deterministic verification as glue

### Takeaway
Across systems, the durable handoff is a structured, versioned artifact (design doc/interfaces, tasks, contract, delta spec) plus an executable check. LLM-generated checks are noisy, so deterministic gates (type-check, lint, import rules, tests with traceability) should be authoritative.

### Cited Findings
- MetaGPT: structured outputs (PRD, system design, interface definitions, file list) with executable feedback adding ~4-5 points [MEASURED] — [MetaGPT](https://arxiv.org/html/2308.00352v7)
- CodeTeam: contract with file ownership, public interfaces, dependency constraints is "machine-checkable"; QA agent iterates on test failures — [arXiv 2606.22082](https://arxiv.org/abs/2606.22082)
- CodeSpec: executable architecture spec + executable behavior spec to keep design and implementation consistent in long sessions (abstract-level) — [arXiv 2607.26777](https://arxiv.org/abs/2607.26777)
- Agentless validation: reproduction + regression tests + majority voting; but generated reproduction tests were unreliable (213 reproduce the issue; only 94 of those pass on the gold patch) — [Agentless](https://arxiv.org/html/2407.01489v2)
- Hexagonal pilot: import-linter/ArchUnit-style checks recommended; Maintainability Index rewarded stubbed code, so structural gates beat aggregate quality metrics — [arXiv 2512.04273](https://arxiv.org/html/2512.04273v1)
- MAST: verifiers that only check compilation are a common failure; a task-objective verification step gave +15.6% — [MAST](https://arxiv.org/html/2503.13657v3)
- Anthropic: store subagent output in external artifacts and pass references to avoid information loss, especially for code — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system); coding is verifiable by tests but human review remains crucial — [Anthropic](https://www.anthropic.com/engineering/building-effective-agents)
- Roo: only a summary returns from subtasks; details not captured are lost — [Roo docs](https://roocodeinc.github.io/Roo-Code/features/boomerang-tasks)
- Kiro: tasks.md is linked to requirements and must be re-synced after spec edits; spec-kit: implement/converge loop until "Converged"; OpenSpec: archive step merges deltas into specs — respective docs above. Spec hashes specifically (as in this repo's `verify --spec-hash`) have no precedent found in the surveyed docs.
- Cursor: CI passing was not sufficient; migration "still needed careful review" — [Cursor](https://cursor.com/blog/scaling-agents)

### Inferences
- The repo's design (packet per item, `covers([...ids])` traceability, spec-hash verification, `notImplemented()` skeleton signal, `compile --check` in CI) goes beyond what Kiro/spec-kit/OpenSpec document; the closest research analogue is CodeTeam/CodeSpec (executable contracts).
- Gate order suggested by evidence: deterministic (types, lint, import-direction, tests-with-covers) before any LLM reviewer, since LLM-generated tests/verifiers are noisy and weak models skip or stub work.

### Gaps
- No source quantifying spec-hash or staleness detection benefits; no source on skeleton-detection signals.

## 5. Review stage: strong-model reviewer/judge, evaluator-optimizer, cost and biases

### Takeaway
Fresh-context reviewers find real defects (Devin Review) and the pattern is endorsed by Anthropic where criteria are clear, but review loops can be endless and LLM judges have documented self-preference and (model-dependent) verbosity biases. Mitigations: cross-family reviewer, hidden authorship, bounded loops with an author-side filter, deterministic gates first.

### Cited Findings
- Devin Review [VENDOR]: reviewer sees only the diff with clean context; ~2 bugs per Devin PR, ~58% severe; coder filters findings with user-intent context to avoid loops; review loops "keep surfacing new bugs and take a long time" — [Cognition](https://cognition.com/blog/multi-agents-working)
- Evaluator-optimizer works "when we have clear evaluation criteria, and when iterative refinement provides measurable value" — [Anthropic](https://www.anthropic.com/engineering/building-effective-agents)
- Anthropic's own eval used an LLM judge on rubric dimensions (accuracy, citations, completeness, source quality, tool efficiency) plus human testing to catch what automation missed — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- Self-preference bias [MEASURED]: GPT-4 shows significant self-preference; explained by lower perplexity (familiarity) of own outputs, which judges rate higher than humans do regardless of authorship — [arXiv 2410.21819](https://arxiv.org/abs/2410.21819)
- 2026 systematic evaluation of judge bias mitigation: verbosity bias is model-dependent (some families favor length; Claude and GPT-4o more quality-sensitive) — [arXiv 2604.23178](https://arxiv.org/pdf/2604.23178) (via search summary; not opened)
- Practitioner guidance (blogs, low-evidence): hide authorship, use judges from different families, shuffle pairwise orders, calibrate against humans — [memx](https://memx.app/blog/llm-as-a-judge-biases-and-fixes/), [futureagi](https://futureagi.com/blog/evaluating-llm-judge-bias-mitigation-2026/)
- Cursor uses a judge agent only to decide continue/stop per cycle, not to certify correctness; output still needed careful human review — [Cursor](https://cursor.com/blog/scaling-agents)
- Cost side: Smart Friend escalates to a larger model only when needed; the strong model is called as a tool with forked context — [Cognition](https://cognition.com/blog/multi-agents-working). Aider's R1+Sonnet reached better than o1 at ~1/14 cost, showing a strong reasoner doing less token-heavy work can be cost-effective — [Aider](https://aider.chat/2025/01/24/r1-sonnet.html)
- MAST: incorrect verification (9.1%) and no/incomplete verification (8.2%) are major failure modes, i.e. LLM reviewers themselves fail — [MAST](https://arxiv.org/html/2503.13657v3)

### Inferences
- A strong reviewer from a different model family than the worker/integrator reduces self-preference exposure; reviewing the diff plus contract rather than the author's narrative reduces anchoring and verbosity effects.
- To avoid endless loops: cap iterations, require findings to cite a spec/invariant ID or a failing deterministic check, and let the integrator (with user/spec context) triage non-spec findings (Cognition's "communication bridge").

### Gaps
- No code-review-specific measurements of self-preference/verbosity found; applying judge-bias research to code review is extrapolation.
- No published cost/benefit numbers for a strong reviewer over cheap-worker output; Devin Review figures are vendor-reported with no baseline.
