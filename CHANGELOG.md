# Changelog

## [Não lançado]

- **Elysia routes and `executeUseCase` can have a deadline (#186):** a use-case run outside an operator awaited `execute` with no bound, so a hung dependency pinned the HTTP request. The new `RuntimeOptions.useCaseTimeoutMs` applies only outside an operator, and leaving it unset means no deadline, the old behaviour. It bounds the execution and the delivery of its events. On expiry it aborts `ctx.signal`, refuses any later publish, and fails with an `AgenticError` coded `runtime.use-case-timeout` (new code), which wins over a refused event, a bus failure or the use-case's own error. An Elysia route maps that code to 504 `{ code, message }`, typed for Eden like the domain 422. A 504 can come after `save` committed, and events already handed to the bus may still be delivered, so a route a client retries should be idempotent. The value is validated like `limits.timeoutMs` (finite, positive, at most 2147483647), and `OperatorRuntime` refuses an invalid one in its constructor. `executeUseCase` / `runUseCase` take it as `options.timeoutMs`. `@agentic-ddd/runtime` now also exports `AgenticError`, `ErrorCode` and `schemaLookup`.

- **Breaking change — `UseCaseContext` has a required `signal` (#164):** a use-case kept running after its operator run timed out, with no way to know. `ctx.signal` is an `AbortSignal` aborted when the run's deadline expires; aborting only notifies, it interrupts nothing, so a long use-case checks it before `save`. Code that builds a `UseCaseContext` by hand must now provide one; `createTestContext` accepts `signal` and provides a never-aborted one by default. The authoring skill and the orders example state the delivery contract: an event is published after `save`, at most once by the runtime, and an outbox in the repository gives at least once.

- **Behaviour change — a failed operator run exposes its error, with two new reasons (#160):** `OperatorRunResult` gains `error`: what the provider, the use-case, the `ApprovalPort` or the event bus threw, the refusal of an undeclared or invalid event, the `ZodError` of an invalid output, or the serialization error of an `invalid_context`. `error` is the raw thrown object: it can hold sensitive data and can be circular, so do not return or log the whole result as is. It is absent on `completed`, `timeout`, `step_limit`, `max_tokens` and `refused`. A failure of the `ApprovalPort` now ends `failed` / `approval_error` and a failure of the event bus ends `failed` / `event_bus_error`; both used to report `use_case_error`, so code that matches on that reason for those cases must match the new ones. `executeUseCase` now rejects with the refusal itself, which names the event, instead of a generic "published an undeclared event".

- **Behaviour change — event payloads are validated against their `@AgentEvent` schema (#163):** the runtime only checked the event name against the use-case's `emits`, so a payload that did not match the declared schema was stamped and delivered. Each published event is now checked against the schema registered under its name before anything is delivered; a mismatch refuses the whole batch like an undeclared event (an operator run ends `failed` / `use_case_error`, an Elysia route answers 500). The payload is only validated, never replaced by the parsed value. Validation is skipped for an event with no `@AgentEvent` schema, and for callers of `executeUseCase` / `runUseCase` that do not pass the new `options.schemaFor`.

- **Behaviour change — a published batch reaches the bus in one call, and a publish that is not awaited is not lost (#183):** `ctx.publish([a, b])` used to call the bus once per event, and a use-case that did not `await` it returned after the first event while the rest was refused in a promise nobody saw. The batch now reaches the bus in one `publish` call (an empty batch does not reach the bus at all), an undeclared event refuses the whole batch before anything is delivered, and the runtime waits for every publish the use-case started before it ends the execution; a publish made after that is refused. A bus failure fails the execution even when the use-case did not await it, swallowed it or threw an error of its own: `executeUseCase` rejects with the bus error and an operator run ends `failed`.

- **Elysia: a second `agentic()` in a sibling sub-app fails the mount (#184):** two sub-apps that each held their own `agentic()` could both be mounted on one app, and `ctx.agentic` silently kept the first runtime. The second mount now fails with the same `Mount one agentic() per app` error as a direct second mount. Still not detected: a plugin that is an async function or a promise, and an `agentic()` mounted inside the app's own `.group()` or `.guard()` when another one is already on the root.

- **Behaviour change — the default event bus no longer keeps events, and a throwing subscriber no longer fails the publication (#161, #162):** `InMemoryEventBus` (the default bus of `OperatorRuntime` and `AgenticModule`) used to append every event to `events` forever; it now keeps them only with `new InMemoryEventBus({ record: true })`, which tests use. A subscriber that throws no longer rejects `publish` or skips the subscribers and events after it: the error goes to the new `onError(error, event)` option, which may be async, or to `console.error` with the event name and id (not the payload). A run therefore no longer ends `failed` because a subscriber threw after the use-case saved. Publications are still delivered one batch at a time for the whole bus, now stated in the class documentation.

## [0.6.0] — 2026-11-09

- **Published on npm as `agentic-ddd`:** the package was called `nestjs-agentic-ddd-architecture` and shipped only as a GitHub release tarball; it is now public on the npm registry. Imports change from `nestjs-agentic-ddd-architecture/<boundary>` to `agentic-ddd/<boundary>` (same eight boundaries, same `agentic-ddd` binary). `private: true` and the `prepublishOnly` gate (`scripts/block-publish.cjs`) are gone; `docs/distribution.md` lists the publication steps.

- **Elysia adapter (ADR-0008):** the same decorated domain mounts on Elysia through `@agentic-ddd/elysia` (`elysia` is an optional peer).
  - `agentic({ ...RuntimeOptions, operators, useCases, http? })` registers the operators and decorates the app with the runtime. Use-cases are passed as instances keyed by the `name` of their `@AgentUseCase`; a different key or a value without the decorator fails the mount.
  - With `http`, each use-case gets `POST {prefix}/use-cases/<name>`, validated by the decorator's zod schemas, and Eden infers the types end to end. `DomainError` answers 422 `{ code, message }`, typed together with Elysia's own validation 422 (`ValidationErrorBody`, which includes its `errors` array) so the client can tell the two apart; any other error answers a generic 500 without the original message. The routes do not go through the `ApprovalPort`; authentication is up to the app (use `onRequest`, which runs before body validation). Operators get no HTTP route (ADR-0007 D5).
  - An instance of a subclass of a declared use-case is accepted (like Nest's `useClass`), and `prefix: '/'` mounts without a prefix. Mount a single `agentic()` per app (a second one fails the mount).
  - `@agentic-ddd/runtime` gains `createRuntime` (used by both adapters) and `executeUseCase`, which runs a use-case outside an operator with the same `emits` rule, now in a guard shared with the operator loop. `runUseCase` does the same with an already validated input: the route uses this path because Elysia hands over a body already transformed by zod, and validating twice would break schemas with `transform`.
  - Route exposure is explicit: `http.routes` lists the use-cases to mount (default: all of `useCases`), and mounting fails when a use-case that an operator lists in `requiresApproval` would be exposed without being named there, since a route skips the `ApprovalPort`. A name in `routes` that is not in `useCases` also fails the mount. Only Elysia's own errors reach the app unchanged (`status()`, built-in classes such as `NotFoundError`, the exact classes registered with `.error()`, not their subclasses); registering a base class such as `Error` lets that exact class through with its message, which is the app's choice, and its subclasses still answer 500. Every other error, an outside client's error with a `status` included, becomes the generic 500, so its status and message never reach the client. `OperatorRuntime` exposes its `registry` and a public `useCase()`; the plugin's approval check reads the registry too. A second `agentic()` on the same app fails the mount (Elysia would keep the first `ctx.agentic`). A use-case's un-awaited `ctx.publish([...])` no longer keeps delivering after the use-case ended: the rest of the batch is dropped (see #183).
  - The import-direction gate bars `elysia` and `@agentic-ddd/elysia` from domain and application, as it already barred Nest.
  - Example in `examples/orders/elysia.ts`.

- **`publish_change` refuses a bundle whose base moved (#156):** `GitHubChangeSink` cuts the branch from the default branch head and commits whole files, so a target file changed on main after the bundle's base ref would have been silently reverted by the pull request. Before creating anything, the sink now makes one call to GitHub's compare API (`GET /repos/{owner}/{repo}/compare/{baseRef}...{headSha}?per_page=1`; skipped when `baseRef` is the head itself; when the answer is `behind` or `diverged`, a second call compares the other way, since three dots diff from the merge base and would miss what only the base changed) and refuses with `publish.base-mismatch` when any changed file (`filename`, or `previous_filename` of a rename), compared case-insensitively like the duplicate-path check, is a path the bundle writes **or the project's lock** (the committed lock must not move either, as `apply.base-mismatch` requires), naming the first such path in bundle order and the real default branch. Mode-only changes (100644 to 100755, symlinks) count, because the compare API lists them. A `baseRef` the host does not know (404, or 422 "No commit found") is `publish.base-unknown`; any other compare error keeps its host code. GitHub lists the changed files only on the first page of a compare, up to 300, so when a comparison reaches 300 files and none is a target the sink fails closed as `publish.host-failed` saying the comparison is too large for GitHub to list in full; an answer without a usable `files` list is `publish.host-failed` ("unexpected answer from the host"). This replaces two recursive tree listings, which truncated, and so refused, on any large repository. Nothing is created on the host in any of these cases, and the token is in no message. `PublishableChange` gains the required `baseRef` and `lockPath` (`publishBundle` passes the manifest's base and the project's lock path; both are repository-relative). New codes: `publish.base-mismatch`, `publish.base-unknown`.

- **`packet` and `verify --item` stop running the whole suite (#159):** `packet` never runs tests any more, with or without `--static` (the flag and `PacketOptions.static` stay, with no effect): its State line is always `<state> (static: tests not run; never certifies done)` and no longer shows `blocked(...)`, which `status` and `next` still report. `verify --item` runs `bun test` only on the test files that quote an obligation id of the item or of its dependencies (any extension and Bun's `_test`/`_spec` names, found by text, so `test.each`, re-exported `test` and literal `[covers: ...]` titles count too), keeping the flags and the configured paths; a command that is not `bun test`, or where a path may be the value of a flag (`--preload ./setup.ts`, `--bail ./src`), still runs whole. Limits: ids must be written as quoted literals in the test file (an id built at run time, or a test declared in a helper file, is not found: the item fails I4 when no other selected file quotes the id, and otherwise that test is simply not judged), and a bare name filter (`app.test.ts`), or a Windows-style path (`.\\src`), stays in the command and keeps running as before. A broken test file that quotes none of those ids no longer fails the item. An item without obligations is now judged by its gates alone, even in a project with no tests (it used to fail with `verify.collection-error`). `verify <NNNN>` still runs the full suite, and the typecheck gate (I5) still covers the whole project.

- **Auth and limits fixes (#157, #158):** a non-JWT bearer token (`abc`, `a.b.c`) is now a 401 `auth.token-invalid` with `WWW-Authenticate` and no JWKS or discovery fetch, instead of a bare 500. An operator with `limits.timeoutMs` above 2,147,483,647 (the `setTimeout` maximum, which clamped it to 1 ms so every run timed out) is now refused at registration (the error names the maximum) and `agentic compile` fails with `validate.operator-limits-invalid` for it.
- **Local CI in a container:** `bun run ci:docker [--head] [--build] [-- <command...>]` runs the `ci` job gate, or any command, in a Linux image built from `docker/ci.Dockerfile` (Bun 1.4.4 as in the CI, plus `crapper`, `dryer` and `mutator` pinned by SHA). It snapshots the working tree through a temporary git index, so uncommitted files are included and the real index is untouched; `--head` snapshots HEAD. Limits come from `CI_DOCKER_CPUS` (default `min(4, host CPUs)`) and `CI_DOCKER_MEMORY`. The default gate is built at run time from the `ci` job of `.github/workflows/ci.yml`, so it cannot drift. The container runs with `--init` and is killed on SIGINT/SIGTERM, the exit code of a failed container wins over the archive's, several words after `--` are shell-quoted, `/out` is chowned to the host user on non-Windows hosts, and a missing `docker` exits 127 with one line. The `evals` job is not covered.

- **Offline rehearsal of the bundle measurement (#122, ADR-0007 D14):** `test/evals-bundle-rehearsal.test.ts` runs the whole path with zero inference: `compileBundle` for a Delta (with a proposal whose `delta:` lists what the Delta adds and changes, or `verify NNNN` reports `proposal.delta-mismatch`), `agentic apply <bundle> --yes`, the scripted adapter standing in for the executor on each item of `agentic next` in wave order (a fixed solution per item, new in `scripts/evals/solutions/shop.ts`, written by the adapter's `before` callback in the test process; it does not read the packet, so this proves the pipeline, not that a packet suffices), `agentic verify --item <item> --spec-hash <hash>` before (must not pass) and after each item, `agentic compile` (the generated dev skill carries source lines) and `agentic verify 0001` returning `done`. `scripts/evals/bundle-rehearsal.ts` holds the per-run record: `bundleRunSchema` (items with attempts, the planned item count, the origin fingerprints before and after, the bundle hash and the `verify NNNN` report, parsed with the existing `changeReportSchema`), `summarizeBundleRun` (initial and final acceptance over the planned items, corrections, certified runs and timeouts; it counts with `scripts/evals/item-tally.ts`, which the cycle-21 aggregate now uses too, so a run is certified only with every planned item accepted, `verify NNNN` `done` and the origin unchanged) and `offlineEnv` (the environment of the `agentic` children: drops variables whose names look like credentials, a denylist that keeps the rest and does nothing about the network). The scripted adapter runs the executor process under bubblewrap with no network and an empty environment, and the test plants credential sentinels in its own environment and checks that process sees none and only the loopback interface; the harness's own git and tar helpers still inherit the test's environment. It needs Linux with bubblewrap and is skipped elsewhere. Left for the real campaign wave: manifests and arms, aggregation, the reading rule, B0 comprehension questions, the P0 Python arm and its frozen tests, token usage and cost in the record. `PREREGISTRATION.md` is now 0.2.0 (rehearsal section only; thresholds, budget and campaign id unchanged).

- **ChangeSink port with a GitHub branch + pull request adapter (#121, ADR-0007 D10):** `src/publish/` defines `ChangeSink.publish(change) -> { branch, url }` and `GitHubChangeSink`, which uses the GitHub REST Git Data API through global `fetch` (no new dependency) and a server-side token passed to its constructor (never read from the change, never put in an error). The branch is always `changes/NNNN-<slug>` (four digits, kebab-case slug), the sink refuses an existing branch (no force-update), and files must be relative POSIX paths under the allowed prefixes given to the constructor. Title and body are capped and `@` mentions are neutralized with a zero-width joiner. Paths never touch `.git`, `.github`, `.gitmodules` or `.gitattributes` (case-insensitive, NFC) and may not collide case-insensitively; files are capped at 1 MiB each and 10 MiB in total; text is capped by code points, the title is one line, and a branch created before a failed pull request is deleted again. Requests never follow redirects, and 429 or an exhausted 403 is `publish.host-rate-limited`. `createFakeGitHost` (in `test/helpers`) is an in-memory host for offline tests. **`publish_change` on the Domain MCP:** the new tool takes a bundle as `propose_change` returned it (`hash`, `files`, and optionally `manifest`; strict: any other key, such as a token, repository or branch, is refused), recomputes the bundle hash from the files with the same code `agentic apply` uses (`apply.hash-mismatch` otherwise), checks every path with the `apply` allow-list (module paths and the one `NNNN-slug` change directory, never `.git`, `.github`, `node_modules` or `.tmp`) and calls the configured `ChangeSink`. What goes into the branch is exactly what `apply` would write: the skeleton files, `changes/NNNN-<slug>/proposal.md` and `examples.json`; packets, briefs, the neutral layer and `BUNDLE.md` stay out. The pull request title is `Change NNNN-slug` and its body carries the bundle hash and base ref (integrity, not authenticity). Over HTTP it needs `change:publish` (all modules) or `change:publish:<module>` (the module comes from the `module` field of the hashed `neutral/model.json`, so it is verified content: a module not in the token, or a bundle that records none, is `auth.scope-missing`; the paths are also narrowed to that module's directories plus the change directory, else `apply.path-forbidden`), separately from `change:propose`; without the scope it is `auth.scope-missing`. stdio is local and unrestricted. The repository and the token come only from the server environment, `AGENTIC_GITHUB_TOKEN` and `AGENTIC_GITHUB_REPO` (`owner/repo`), read by `agentic-ddd mcp`; half or malformed values exit 1 with `publish.config-invalid` (the token is never printed), and the sink may only write under the module paths and the changes directory of the project config. With no sink configured, or when serving a published lock, the tool answers `mcp.publish-unavailable`. It reuses the 256 KiB input cap and, like `propose_change`, a one-call-at-a-time guard (`mcp.publish-busy`). The tool is the only one with `readOnlyHint: false`. Inside `apply`, `verifyBundle`, `plan`, `checkedWrites` and `writableDirs` are shared by apply and publish, and the new `splitBundleEntries` splits a bundle held in memory the way `splitBundleFiles` splits a directory (no behaviour change). New codes: `mcp.publish-busy`, `mcp.publish-unavailable`, plus the `publish.*` codes above.

- **`agentic apply <bundle-dir>` (#120, ADR-0007 D10):** applies a bundle written by `compileBundle` to a project at its base. It first recomputes the bundle hash from the files on disk (LF-normalized, same canonical rule as the manifest) and refuses a tampered, missing or extra file with `apply.hash-mismatch`. It then checks the base: the committed lock at `HEAD` must hash to `baseLockHash`, `baseRef` must exist, and every file the bundle would write must equal its content at `baseRef` (a locally modified or untracked target file is refused), all as `apply.base-mismatch` naming the first path; an existing `changes/NNNN-*` is `apply.change-exists`. Writes are staged under `<project>/.tmp` and moved into place all-or-nothing, keeping backups until the end: a failed write is `apply.write-failed` and a failing `compile` is `apply.compile-failed`; a failed write leaves the tree byte-identical, and a failed compile restores the bundle's files (the files `compile` regenerated are not restored, the message says to run `bun run agentic compile`). It writes the skeleton files, `changes/NNNN-<slug>/proposal.md` and the Delta examples as `changes/NNNN-<slug>/examples.json`, never packets, briefs or `BUNDLE.md`, then runs `compile` (child process, 120 s limit and killed on expiry as `apply.compile-timeout`, environment reduced to PATH and the platform variables, no tokens). **Integrity, not authenticity:** the hash proves the bundle is unchanged, not who made it, so the bundle is untrusted input. `apply` writes only under the `path` of a module of the project config and inside exactly one `changes/NNNN-slug/` directory (`^\d{4}-[a-z0-9]+(-[a-z0-9]+)*$`, else `apply.change-invalid`); anything else, `.git`, `.github`, `node_modules` and `.tmp` segments (any case), root files and paths that resolve through a link out of the allowed root are refused with `apply.path-forbidden` before anything is written, and a path escaping the project is `apply.path-escape`. Without `--yes` it prints the files it would write (new or overwritten), the bundle hash and the integrity caveat, writes nothing and exits non-zero with `apply.confirmation-required`. An exclusive `.tmp/apply.lock` serializes applies (`apply.locked`, delete the file if no apply is running); SIGINT/SIGTERM during write or compile roll back and exit 130. Git reads use `<ref>:./<path>`, so a project below the git root works. The old proposal-archiving module `src/compiler/changes/apply.ts` is now `archive.ts` (no behaviour change). New codes: `apply.base-mismatch`, `apply.change-exists`, `apply.change-invalid`, `apply.compile-failed`, `apply.compile-timeout`, `apply.confirmation-required`, `apply.hash-mismatch`, `apply.locked`, `apply.path-escape`, `apply.path-forbidden`, `apply.rollback-failed`, `apply.write-failed`. **Trust:** applying runs the bundle's code, because `compile` imports the module files with your privileges, so apply only bundles you trust (the confirmation text and the usage say so; sandboxing is not done). A rollback that cannot restore a file keeps going, keeps the `.tmp/apply-*` stage with the backups and names it in `apply.rollback-failed`. A dry run or a refused base leaves no `.tmp` behind; the change number is checked again under the lock and also against `changes/archive/`; a bundle that already ships `examples.json` is `apply.change-invalid`. **Breaking:** a bundle without a proposal (no change directory) is refused with `apply.change-invalid`.

- **`propose_change` on the Domain MCP (#118, ADR-0007 D8-D13):** the new tool takes `{ delta, proposal: { slug, markdown } }` (strict: any other key is refused; `proposal` is required, because the bundle's `changes/NNNN-slug/` directory comes from it and `apply` refuses a bundle without exactly one), checks the Delta, runs `compileBundle` and returns the bundle (`manifest`, `hash`, `files` with `BUNDLE.md`) as JSON. Over HTTP it needs `change:propose` (all modules) or `change:propose:<module>`; a token scoped to another module, or without the scope, gets `auth.scope-missing`. stdio is local and unrestricted, like the other tools. The base (`HEAD` of the served working copy), its conventions, the timeout, the temp location and the proposal number (next after the base lock changes) come only from the server; a published-lock server answers `mcp.propose-unavailable`. Inputs over 256 KiB serialized are refused before any work with `mcp.input-too-large` (the HTTP body was already capped at 1 MiB). Nothing is stored after the call. Delta errors come back as tool errors with their code and offending paths. The tool is not read-only (`readOnlyHint: false`, `destructiveHint: false`, idempotent): it creates a git worktree and runs processes on the server, one at a time (`mcp.propose-busy` when another is running); `mcp --config` also names the config the compile uses, and the HTTP idle timeout is 255 s so a slow compile keeps its connection. New codes: `mcp.input-too-large`, `mcp.propose-busy`, `mcp.propose-unavailable`.

- **Compiled bundle with the `nestjs-ts` target (#118, ADR-0007 D8-D10):** the new library function `compileBundle({ delta, baseRoot, baseRef, proposal, ... })` (exported from `@agentic-ddd/compiler`; the `propose_change` MCP tool calls it; the optional `configPath` names the project config when it is not `<baseRoot>/agentic.config.ts`, and `baseRoot` need not be the repository top) renders a Delta onto a detached git worktree of the base commit, splices fragments into the existing files, runs `compile` on that candidate tree in a child process with a timeout (default 120 s, killed on expiry, scrubbed environment, `--no-install`) and returns a stateless bundle: `BUNDLE.md` (items in wave order with the exact `packet`, `verify --item ... --spec-hash` and `apply` commands), `bundle.json` (`{ version, baseRef, baseLockHash, layers: { target }, examples, files: [{ path, sha256 }], hash }`) and the target files (skeleton as full file contents, one packet per item with its `specHash` computed on the candidate tree, the module dev skill, the required proposal under `target/changes/NNNN-slug/`). The worktree is removed on every path, success, error or timeout, so nothing is kept. The bundle hash is the sha256 of the canonical JSON (sorted keys, no whitespace, files by path, LF content) of everything except the hash field, so the same Delta on the same base commit gives byte-identical output. Executor briefs come from the same generator as `scripts/agent-briefs.ts` (now `renderBrief` in `src/compiler/briefs.ts`), with the team rules of the base commit and their token budget; a brief that cannot be rendered is `bundle.brief-invalid`. The analysis lists the items of the Delta module that changed plus the pending items they depend on (the same selection as `agentic status --change`), never those of another module; the child writes its result to a file, not to stdout. Server paths (base root, worktree) are hidden in every error text sent to clients. New codes: `bundle.base-lock-missing`, `bundle.base-unknown`, `bundle.brief-invalid`, `bundle.compile-failed`, `bundle.compile-timeout`, `bundle.config-missing`, `bundle.delta-invalid`, `bundle.module-unknown`, `bundle.path-escape`, `bundle.proposal-invalid` (the slug is not kebab-case).

- **Neutral layer in the compiled bundle (#119, ADR-0007 D10-D12):** `compileBundle` now also returns `layers.neutral` (`{ model, readme, briefs }`) with the files `neutral/README.md`, `neutral/model.json` and one `neutral/briefs/<item>.md` per item, all LF and covered by the bundle hash. The model is built from the validated Delta and the proposal, with no candidate code involved: new and extended entities (an existing entity lists only the members this change adds), value objects, events, ports and use-cases with language-neutral types (`text`, `number`, `boolean`, `timestamp`, `list of X`, `nothing`), the state transitions the Delta declares on methods (an empty list when it declares none, none are inferred), every invariant (`invariant:<Entity>/<id>`) with its text and given/when/then examples (at least one, enforced), and the acceptance criteria of the proposal. The briefs describe each item's job without TypeScript syntax, paths, decorators, imports or commands. The neutral layer has no `done` certification (D12), and `BUNDLE.md` now explains both layers. `bundle.json` gains `layers.neutral`, so bundle hashes change.

- **Delta additions to existing entities and use-cases (#144, ADR-0007 D8, D9):** a Delta can now carry `entityAdditions` (`{ entity, invariants, methods }` for an entity of the base: new methods, invariants and states-checked transitions), `useCaseAdditions` (`{ useCase, uses, emits }`) and `events` whose `entity` is an existing one. Existing files are never re-rendered (that would destroy hand-written bodies): `renderDelta` returns `fragments` (new class members, class decorators, `uses`/`emits` elements, appended event classes, plus the imports they need, per module-relative path, sorted) next to `files`. The new pure `splice(source, fragment)` inserts a fragment through the TypeScript AST (members before the class closing brace, decorators after the last one, array elements after the last element, imports merged into the existing declaration and sorted) and refuses, never guessing, with `delta.splice-anchor-missing` (class, decorator or array not found) or `delta.splice-unexpected-shape` (does not parse, member or import conflict). It does no I/O and no hash check (`agentic apply` does those, #120). Every new invariant now carries `examples: [{ given, when, then }]` (at least one, capped by `LIMITS.examples` and `LIMITS.exampleText`); `@Invariant` has no such option, so they are returned as `examples` in the render result for the neutral layer and never written into TypeScript. Removing or renaming stays out of scope: a removal-like key fails as `delta.schema-invalid` with its path, and re-adding an existing method, invariant, use or emit fails as `delta.name-collision`. New codes: `delta.splice-anchor-missing`, `delta.splice-unexpected-shape`. **Breaking for Delta producers:** invariants without `examples` are refused.

- **Delta schema and deterministic skeleton renderer (#117, ADR-0007 D8, D9):** `validateDelta` checks a JSON Delta for one module (entities, value objects, invariants with `id` and `text`, methods, events, ports and use-cases with `uses`, `emits` and `ports`) with a strict zod schema, and `renderDelta(delta, { conventions, base })` renders decorated TypeScript with `notImplemented()` bodies, laid out by the resolved conventions (layer folders, events suffix), in canonical order: the same Delta and base give byte-identical files, whatever the order of the input arrays (an entity's `states` keep their declared order, which is the lifecycle order). Identifiers must match an allowlist, types come from a small grammar (`string`, `number`, `boolean`, `Date`, a declared entity or value object, `T[]`, optional fields and parameters marked `name?`, `void` returns), and every client string (`description`, `text`, `whenToUse`, state names) is emitted only as an escaped literal, never as code (D9). Only new items are supported: a name that already exists in the base is refused as `delta.name-collision` (additions to existing items are tracked in #144). Every array has a cap (`LIMITS`), text must be non-empty after trim, class names (entities, value objects, ports, events, use-case classes) share one namespace that also covers the base, references only resolve inside the Delta's module, a required parameter cannot follow an optional one, entity method names cannot clash with built-ins or inherited members (derived from `AggregateRoot`; port methods only with `Object` members), class and parameter names cannot be a name the renderer imports or a reserved word (field and method names can), a use case's `emits` must list exactly the events of the methods in its `uses`, and a state cannot be blank. `renderDelta` has a required option `existingFiles` (module-relative paths already in the module, supplied by the caller): a rendered path equal to one of them, ignoring case, is refused as `delta.path-collision`. Errors are sorted by path, code and message. A shape error (`delta.schema-invalid`) stops validation before the semantic checks run, so fix those first and revalidate. Client strings echoed in messages are JSON-quoted and truncated to 80 characters, and unknown keys are listed at most five at a time with a count. File-name stems that Windows reserves (`CON`, `PRN`, `AUX`, `NUL`, `COM0-9`, `LPT0-9`), port names whose lower-camel form is a reserved word, and use-case names over 64 characters are refused as `delta.invalid-identifier`. `LIMITS` is exported from `@agentic-ddd/compiler` as `DELTA_LIMITS`. The renderer is pure library code: no CLI command and no MCP tool yet. New codes: `delta.invalid-identifier`, `delta.name-collision`, `delta.path-collision`, `delta.reference-unknown`, `delta.schema-invalid`, `delta.type-invalid`.

- **Authoring skill over the Domain MCP (#116):** the new read-only tool `authoring_guide` (index without arguments, one document with `doc`) and MCP resources under `skill://` serve the `agentic-ddd` authoring skill, the `<module>-dev` skills (rendered from the scoped lock, so they also work with a published lock) and the team rules (only rules with a file; a module-scoped token sees a path-bound rule through its globs after brace expansion, minus those that contain the name or path of a module it cannot read, so rules for tests and infrastructure stay visible; `rules_for_path` uses the same cut and no longer returns `examples/{orders,billing}/**` to an orders-only token). Over HTTP they need the new scope `skill:read` (all modules) or `skill:read:<module>`; a token with `skill:read` and no `domain:read` reaches only these documents and sees no domain data, and a token with neither is still refused with `auth.scope-missing` at the gate, and a token without `skill:read` that reaches `authoring_guide` is told the scope is needed. The authoring skill is read once per server from the installed package and does not need the snapshot, so it works before the first compile; it is not covered by the published digest. A hidden document answers exactly like an unknown one (`mcp.doc-unknown`); runtime skills are never served. The server `instructions` and the tool description carry the language rule (reply in the user's language, never translate identifiers). The resource server gains `anyOfScopes` (an empty list is no constraint), and the package now ships `skills/agentic-ddd` (`SKILL.md` and `references/`). The tutorial reference no longer uses `/tmp` paths (its scratch directory is `../agentic-tasks`, outside the checkout). New code: `mcp.doc-unknown`. The MCP snapshot (`.agentic/mcp/snapshot.json`) and the published lock now carry the project's resolved `conventions`, and the published lock digest covers them too, so the MCP dev skills match what `compile` writes. A snapshot written before this change has no `conventions` and is reported as stale (run `agentic compile` again). A published lock without the field is rejected as `published.malformed`; nothing was published before this change, so the published lock format stays at version 1. When the authoring skill is missing on the server, the dev skills and team rules are still served, and `authoring_guide` says the authoring skill is unavailable (new code: `mcp.skills-unavailable`).

- **Domain MCP serves a published lock (#114, ADR-0007 D2):** `agentic-ddd publish-lock --version <v> --out <file>` writes a JSON artifact from the compile snapshot (`publishedLockVersion`, `version`, `digest`, `lock`, `rules`); the digest is the SHA-256 of the canonical `{ version, lock, rules }` and is recomputed on read, which detects corruption (tampering is only stopped by pinning `--expect-digest` out of band). `agentic-ddd mcp [--http] --published <file> [--expect-digest <sha256>]` serves that file instead of the working copy: it is read and verified once at startup, never touches the disk again, and refuses absolute paths in `rules_for_path`. Working-copy mode keeps its per-call freshness check, and module scoping is identical in both modes. The new read-only tool `domain_source` reports `{mode, version, digest}` (or `{mode: 'working-copy'}`), and the startup line names the version and the digest prefix. The default bind stays `127.0.0.1`. The demo `bun run mcp:demo` (after `bun run agentic compile`) runs an issuer, the MCP and a client on loopback and checks the 401, the scopes and `domain_source`; it speaks JSON-RPC over `fetch`, so no MCP client SDK was added; `--keep-alive` keeps it running so a real client can connect. Documented in `docs/mcp-remote-demo.md`. New codes: `published.digest-mismatch`, `published.digest-unexpected`, `published.malformed`, `published.unreadable`, `published.version-invalid`, `published.version-unsupported`, `cli.expect-digest-requires-published`.

- **Module-scoped read access on the Domain MCP (#113, #139, ADR-0007 D4):** a token may carry `domain:read:<module>`; the bare `domain:read` still means every module and wins over suffixed scopes, several module scopes are a union, and a token with only module scopes passes the gate. A token with neither gets `auth.scope-missing` (403) as before. A module scope naming a module that does not exist gives empty `domain_overview` and `domain_changes` results, while `domain_element` and `rules_for_path` refuse as for any out-of-scope id or path (`mcp.element-unknown`, `mcp.path-out-of-scope`). For a module-scoped token, `domain_overview` lists only its modules; `domain_element` answers an id in another module exactly like an unknown id (`mcp.element-unknown`); relation ids that point into hidden modules are removed from visible elements; `domain_changes` shows a change only when it has at least one item and every item is in scope; `rules_for_path` answers only for paths inside an in-scope module (otherwise the new `mcp.path-out-of-scope`), and narrows each returned rule's `paths` to the globs that match the requested path (rule bodies are returned as written: they are repo-wide team conventions). stdio (`agentic-ddd mcp`) is unchanged and sees everything, because it is local and unauthenticated. The absolute project root no longer appears in `mcp.path-outside-root`; over HTTP, `snapshot.missing` gives a generic message and unexpected errors answer `Internal server error`. `agentic-ddd mcp --http` bind failures: `EADDRINUSE` gives `cli.port-in-use`, `EACCES` gives the new `cli.port-denied`, and `EADDRNOTAVAIL` gives the new `cli.host-unavailable`; all three exit 1, and any other bind error surfaces unchanged. With Bun 1.4.4 on Windows every failed bind is reported as `EADDRINUSE`, so there a privileged port or a `--host` the machine does not own prints `cli.port-in-use`; on Linux the bind reports `EACCES`/`EADDRNOTAVAIL` and the new codes appear (macOS not verified). New codes: `mcp.path-out-of-scope`, `cli.port-denied`, `cli.host-unavailable`.

- **Follow-ups to the MCP HTTP server (#137, from #136):** the rule "https, or http on a loopback host" now exists once, as `isSecureOrLoopbackUrl` in `src/contracts/url.ts`, and the config validator (`mcp.issuer`, `mcp.resource`, `mcp.jwksUri`) and the discovered `jwks_uri` check both use it, so the copies cannot drift. Loopback now means the whole `127.0.0.0/8` block, `[::1]` and `localhost` (before, only `127.0.0.1`, `[::1]` and `localhost`), so `http://127.0.0.2:9000` is accepted as an issuer. The Host/Origin allowlist is unchanged: it is not this rule but the set of names that can stand for one listener. `agentic-ddd mcp --http` on a port that is already in use now prints `[cli.port-in-use]` and exits 1, instead of an uncoded error. New code: `cli.port-in-use`. Two unreachable branches of the auth error mapping (`auth.audience-mismatch` and `auth.token-expired` guessed from the SDK's message text) are gone; those refusals are produced earlier, by the verifier, with the same codes.

- **Domain MCP over Streamable HTTP (#112, ADR-0007 D2–D4):** `agentic-ddd mcp --http [--port 3333] [--host 127.0.0.1]` serves the four read tools behind an OAuth 2.1 resource server. The authorization server stays external: set `mcp: { issuer, resource, jwksUri? }` in `agentic.config.ts` (without `jwksUri` it is discovered through RFC 8414, then OIDC). Bearer JWTs are verified with `jose` (asymmetric algorithms only: RS256, PS256, ES256, ES384, EdDSA; `iss`, `aud` and `exp` checked, `exp` with no tolerance) and must carry `domain:read`. Refusals keep the OAuth error and carry a stable code in `error_description`: `auth.token-missing`, `auth.token-invalid`, `auth.audience-mismatch`, `auth.issuer-mismatch`, `auth.token-expired`, `auth.scope-missing`. Protected Resource Metadata (RFC 9728) is served at the well-known URL. `jose` is an optional peer dependency, needed only for `--http`. The resource-server module (`src/auth/resource-server.ts`) knows nothing about tools, so the Runtime MCP can reuse it. Scopes are read from `scope` and `scp` (string or array), and a trailing slash on `resource` is accepted either way. The default bind is `127.0.0.1`; stdio mode is unchanged. Requests are checked against a Host/Origin allowlist (the bind address and the configured `resource`, plus loopback aliases on a loopback bind) as a DNS-rebinding defense; a request without an `Origin` header is allowed. New codes: `config.mcp-url-invalid`, `config.mcp-field-missing`, `cli.http-option-requires-http`, `cli.port-invalid`, `cli.mcp-config-missing`, `cli.jose-missing`, `mcp.host-denied`, `mcp.origin-denied`.

- **Breaking change (#111, ADR-0007 D13):** CLI, `compile`, `verify`, packet and MCP messages are now English, and every error carries a stable code (for example `config.key-unknown` or `verify.docs-outdated`), so an agent can explain it in the user's language. The codes and their meaning are listed in one place, `ERROR_CODES` in `src/contracts/codes.ts` (exported with `ErrorCode`, `AgenticError` and the `formatCoded` formatter by `@agentic-ddd/compiler`). `CompileError` and verify `Finding` gain a required `code` field, which `--json` reports carry. Thrown errors are an `AgenticError` with `code`. Human output prints `message [code]`; warnings and static-test diagnostics, which never fail a command, stay uncoded. Match on the code, not on the text. Packet headings change too (`## Specification`, `## Test obligations`, `## Executor rules`, `## Verification command`), as do the gate names in verify reports. Domain errors from `@agentic-ddd/core` and the `scripts/` tooling are unchanged.

- **Breaking change (#109, ADR-0007 D13):** the text `compile` generates is now English only, with no language option: the dev skills (`<module>-dev`), the operators' runtime skills, the `history.md` and `state-machine.md` references, the `AGENTS.md` block and the generated-file header. The operator runtime's tool descriptions also switch to `When to use:` / `When not to use:`. The core rules (`core/...`) were translated too, but their keys and `{{…}}` markers did not change, so a team rule that overrides one still applies. The proposal section keeps its name, `## Motivo`, and so does the matching history column. Business text (descriptions, invariant `text`, `instructions` and proposals) stays in the author's language. Running `bun run agentic compile` regenerates everything; until then, `compile --check` reports the old generated files. Packets and CLI messages follow in #111.

- **Windows nativo (#128):** o framework passa a funcionar no Windows sem WSL, e o CI ganha o job `ci-windows`, com o mesmo gate do `ci` em `windows-latest`.
  - O `compile` falhava em qualquer projeto: `parseFrame` só reconhecia caminhos POSIX, e todo decorator ficava com origem `<desconhecido>`. Agora ele aceita letra de unidade, UNC e `file:///C:/`.
  - O `compile --check` acusava o espelho de skill desatualizado, porque o `readlink` devolve `\`.
  - O `skills:install` grava os links dos adaptadores com `/`, então o adaptador é idêntico em qualquer sistema. Quem já instalou no Windows precisa remover os adaptadores `agentic-ddd-*` de `.claude/agents`, `.codex/agents` e `.cursor/agents` e rodar `skills:install` de novo, porque o texto antigo conta como conflito.
  - O tutorial `skills:example` grava os caminhos do framework com `/`.
  - O `test:package` extrai o pacote com caminhos relativos, porque o GNU tar do Git Bash lia `C:` como host remoto.
  - Raiz com nome curto 8.3 (como o da pasta temporária dos runners) ou em outro disco: o `compile` importava o domínio com outra instância do registry, e o snapshot do MCP montava caminhos inválidos. Conforme a versão, o Bun grava os frames com o nome curto ou com o longo. Agora `canonicalPath` (de `@agentic-ddd/decorators`) expande só os nomes 8.3, sem trocar drive `subst` ou mapeado pelo destino, e é aplicado uma vez na origem: no arquivo do `captureSource`, na raiz e no `--out-root` do `resolveConfig`, e nas raízes recebidas de fora (`buildIR`, `declarationsInModules`, `checkSnapshot` e caminho absoluto da tool MCP). A raiz do snapshot é resolvida com `resolve`.
  - **Segurança:** `rules.dir` fora da raiz, a tool MCP `rules_for_path` com `..\`, `./../` ou `x/../../` e o `within` do harness de evals aceitavam caminhos fora da raiz, porque a checagem só via um `../` inicial. Agora o caminho é normalizado antes de ser comparado.

- **Mudança de compatibilidade (#110, ADR-0007 D13):** a skill autoral `skills/agentic-ddd` (SKILL.md e referências), os núcleos de papel (`ROLE_CORES`), o texto dos briefs de executor e revisor e os adaptadores instalados por `skills:install` passam a ser só em inglês. Quem tem adaptadores instalados precisa removê-los e reinstalar (o texto antigo conta como conflito). Os briefs e os núcleos ganham a linha que manda manter identificadores, IDs de regra e texto de negócio sem tradução, e a skill manda responder ao usuário no idioma dele. Os rótulos do packet, as mensagens de erro e os tutoriais de exemplo (`tasks`, `matriculas`) não mudam nesta etapa. O texto medido no cycle-21 e no benchmark de revisão muda; o snapshot `agent-briefs` e o hash da árvore do tutorial foram regenerados.

See [docs/releases/0.6.0.md](docs/releases/0.6.0.md).

- Lock, propostas de mudança, reconciliação, histórico, cobertura por `covers` e verificação G1–G7.
- Coordenação por `status`, `next`, `packet` e `verify --item`, com proteção por `specHash` e consultas antes de existirem testes.
- Runtime sequencial com FakeLlm, aprovação, validação Zod, eventos, IDs, traces e limites; contexto inválido retorna `invalid_context`.
- Composição Nest de operators/use-cases e exemplo orders, preservando o isolamento do domínio e BunAdapter.
- E2E de criação/confirmação de pedido, aprovação negada/concedida, coordenação em quatro ondas e inicialização do bundle.

### Limites desta release

- Runtime demonstrado com FakeLlm; adapter de provider real e CLI interativa estão nos próximos planos.
- Timeout fecha a admissão de tools/publicações, mas não interrompe à força nem desfaz operações já iniciadas.
- Bundle requer o source map para preservar localização e hash das declarações.
- Publicação reentrante no mesmo bus durante um handler é rejeitada; `reactsTo` por fila está no backlog.
- A change de exemplo 0002 mantém um critério manual de copy, demonstrando `needs-human` apenas por G6. Isso não representa falha automática nem cancelamento da release.
- Distribuição nesta versão é pelo código-fonte GitHub; instalação como pacote npm possui issue de preparação própria.
